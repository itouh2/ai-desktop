# ai-desktop: ゲーム専用にしない作り直し（道具・使い方・知見の分離）設計書

- 日付: 2026-10-05
- 状態: 実装済み（2026-10-05）
- 前提: [ページのボタン](2026-10-03-page-buttons-design.md)、[move_mouse](2026-10-05-move-mouse-design.md)

## 1. 目的

ai-desktop を、いろいろなゲームとアプリ操作に使える道具にする。

Slay the Spire 2（以下 STS2）の助言セッション（2026-10-04〜05）を重ねるうちに、スキルと知見がゲーム寄りになった。

- スキルの例が HP・敵の攻撃・「ターン終了した」などゲームのものばかり
- 知見の置き場所が `docs/games/` に固定され、ai-desktop 自体の説明（`docs/`）と混ざっている
- アプリを問わない使い方のコツが、STS2 のノートに埋もれている
- STS2 の知見の層が崩れている（敵の表が 3 か所に分かれ、ゲーム共通の事実がキャラ別ファイルにある）

これを、道具（MCP）・使い方（スキル）・知見（notes）の 3 つに分け、どれも特定のアプリに依存しない形にする。あわせて、STS2 のセッションで見えた「どのアプリでも要る」MCP の不足を直す。

## 2. 決定事項

| 項目 | 決定 | 理由 |
|---|---|---|
| 「汎用」の意味 | いろいろなゲームとアプリ操作に使えること。配布はしない | ユーザーの回答（2026-10-05） |
| 操作する人 | 今回は「Claude が見て案内し、操作はユーザー」。Claude 自身のクリック・入力は次の段階で、構成に余地だけ残す | ユーザーの選択 |
| 方式 | 道具・使い方・知見を分ける | ユーザーの選択。3 案（フォルダ内で言い回しだけ汎用化／MCP が知見も扱う）から |
| 使える範囲 | ai-desktop フォルダの中だけ。スキルも MCP もこのフォルダで動かす | ユーザーの指示（2026-10-05） |
| MCP の登録 | ユーザー全体の登録をやめ、このフォルダの `.mcp.json` に書く | 同上 |
| 知見の名前と場所 | リポジトリ直下の `notes/` | `docs/` は ai-desktop 自体の説明の置き場。ユーザーの選択 |
| 「更新」 | ページに常に出す。Claude はボタンに入れない | どのアプリでも要る。STS2 では毎回 Claude が付けていた |
| 撮影の保持数 | 10 → 20 件 | 説明文を何か所も読むと元の撮影が消えた（STS2 で発生） |
| MCP と知見 | MCP は知見を扱わない。読み書きはスキル（Claude）が行う | MCP は「目」に徹する（最初の設計の方針） |

## 3. スコープ

### 含める

- MCP: 「更新」ボタンの常設、`html` の省略、撮影の保持数、ボタン名「更新」の予約、説明文の手直し（§5）
- MCP の登録をこのフォルダへ移す（§5.5）
- スキルの書き直しと手引き 3 つの新設（§6）
- `notes/` の新設と、STS2 の知見の移し替え・整理（§7）
- README とメモリー（Claude の自動メモリー）の更新

### 含めない

- Claude 自身のクリック、文字入力、キー操作（次の段階。§10）
- 撮り直す対象の変更（表示中と同じウィンドウかモニターのまま）
- MCP による知見の読み書きや自動添付
- 別のフォルダからの利用（必要になったら、ユーザー全体の登録かプラグインにする）
- 古い設計書・計画（`docs/superpowers/`）の中のリンク修正。履歴としてそのまま残す
- 以前の `wait_for_message` の長時間停止（10007 秒。再現していない）の調査

## 4. 全体構成

```text
C:\Works\2026\ai-desktop\
  .mcp.json                         MCP の登録（このフォルダだけで有効）
  .claude\skills\ai-desktop-guide\  使い方（スキル。このフォルダだけで有効）
    SKILL.md                        どのアプリでも共通の手順
    references\
      annotation-html.md            注釈 HTML の書き方（今のまま）
      playbook-game.md              ゲームの案内（新規）
      playbook-app.md               アプリ操作の案内（新規）
      notes-format.md               知見の書き方（新規）
  src\ai_desktop\                   道具（MCP）
  notes\                            知見（アプリごとのフォルダ。新規）
  docs\                             ai-desktop 自体の説明（設計書・計画・レビュー）
```

| 層 | 役割 | 持たないもの |
|---|---|---|
| 道具（MCP） | 見る（撮影）、示す（注釈ページ）、聞く（ボタン・入力欄・更新）、カーソルを乗せる | どのアプリの知識も持たない |
| 使い方（スキル） | どのアプリでも共通の手順。場面ごとの違いは手引き（playbook）に分ける | アプリ固有の事実 |
| 知見（notes） | アプリごとの事実・コツ・その回の記録 | アプリを問わない使い方のコツ（それはスキルへ） |

将来 Claude 自身の操作を足すときは、MCP に道具を加え、手引きに「Claude が操作する場面」を書き足す。構成は変えない。

## 5. MCP の変更

### 5.1 「更新」ボタンの常設

ページ（`annotate.py`）:

- 返事の欄（`#bar`）の先頭に、Claude のボタンとは別に `<button id="refresh" type="button">更新</button>` を置く
- 見た目は枠線だけにして、Claude のボタン（赤の塗りつぶし）と区別する
- 欄が出る条件は今と同じ（`buttons` か `message_box` があるページ）。押せるのは待ち受け中だけ（ほかのボタンと同じく `syncControls` で切り替える）
- 押すと `POST /refresh`（本文 `{}`）。結果の表示とエラー時の戻し方は、ボタンの `press` と同じ

サーバー（`viewer.py`）:

- `Viewer.refresh()` を加える。待ち受け中でなければ `NOT_WAITING_MESSAGE`、表示中のページがなければ既存の「表示中のページがありません」。それ以外は `{"message": "", "via": "refresh"}` で待っている呼び出しを起こす（`_answer`）
- 要求の処理に `/refresh` を加える。トークン・`Host`・`Origin` の検査は、ほかの POST と同じ

ツール（`server.py`）:

- `wait_for_message` の戻り値に `via: "refresh"` が加わる。説明文に「`via` が `"refresh"` なら、ユーザーがページの『更新』を押した。届いた撮り直し画像で状況を読み直し、今の手順を出し直す」と書く
- `buttons` に「更新」（前後の空白を除いて一致）を入れたら、`ToolError`「「更新」はページに常に出ているので、buttons に入れないでください。」

### 5.2 `html` の省略

- `show_annotated(capture_id, html="", ...)` とし、空や空白だけでも受け付ける。注釈のないページ（画像と説明文だけ）になる
- 長さの上限（10 万文字）は今のまま
- 用途: 案内を終えるとき（入口なしで呼んで「考え中」を解除する）、画像と説明文だけを見せたいとき
- ツールの説明文の `html` の項に「省略すると注釈のないページになる」と書く

### 5.3 撮影の保持数

- `captures.py` の `CAPTURE_LIMIT` を 20 にする
- 「直近 10 件」と書いた箇所（`show_annotated` と `move_mouse` の説明文、スキル）を 20 件に直す
- メモリーの増加: 背景用の JPEG（縮小前、品質 90）が最大 20 枚。4K モニターの撮影ばかりでも 50MB 前後

### 5.4 説明文とコメント

- `INSTRUCTIONS`（1 段落のまま）に次を足す
  - ページには「更新」が常に出る。`via` が `"refresh"` なら、撮り直し画像で読み直して手順を出し直す。`buttons` に「更新」は入れない
  - 終えるときは、入口なし（`html` も省略してよい）で `show_annotated` を 1 回呼ぶ
- `viewer.py` の `AFTER_CLICK_SECONDS` のコメントを「アプリ（特にゲーム）はクリックを後のフレームで処理することがある」に直す
- README のツール一覧（`show_annotated`、`wait_for_message`）と使い方の例を直す

### 5.5 MCP の登録をこのフォルダへ移す

- リポジトリ直下に `.mcp.json` を作る。秘密情報を含まないので git に入れる

  ```json
  {
    "mcpServers": {
      "ai-desktop": {
        "command": "uv",
        "args": ["run", "--no-sync", "--directory", "C:/Works/2026/ai-desktop", "ai-desktop"]
      }
    }
  }
  ```

  `--directory` は今の登録と同じ絶対パスにする（Claude Code を開いた場所に左右されないため）
- ユーザー全体の登録を消す: `claude mcp remove ai-desktop -s user`。消すと、別のフォルダで開いた Claude Code からは ai-desktop が見えなくなる（意図どおり）
- firecrawl はユーザー全体のまま（汎用の検索なので）
- フォルダ単位の MCP は、最初に開いたときに Claude Code が使ってよいかを一度だけ確認する。承認はユーザーが行う
- README の「Claude Code への登録」を、`.mcp.json` を使う手順に書き換える（`--no-sync` の理由の説明は残す）

## 6. スキル

### 6.1 `SKILL.md`（使い方の核）

本文にゲーム固有の言葉（HP、ターン、カード、敵、レリック、ポーション、デッキなど）を書かない。例は「できた」「保存した」「見つからない」など、どのアプリにも通じるものにする。

| 節 | 内容 |
|---|---|
| 1. 撮影の選び方 | 1 つのウィンドウで済むなら `capture_window`（ゲーム、全画面のアプリ）。ダイアログ・メニュー・ツールチップが別ウィンドウで出るアプリ操作は `capture_monitor`。演出や読み込みの途中は撮り直す。見えている事実と推測を分ける |
| 2. 注釈で示す | 今の内容。説明文は「1 行目に状況、空行、手順を 1 行に 1 つ、最後に補足」。状況の例は汎用にする（画面の状態、数値、残り時間など）。保持数は 20 件 |
| 3. ページでのやりとり | 入口（ボタン・入力欄）の選び方、`wait_for_message` の繰り返し（null が 5 回で止める）。「更新」はページに常にあるので入れない。`via` ごとの反応（button / text / refresh）。報告を受けたら、撮り直し画像で期待どおり進んだか確かめる。終わり方（入力欄に「終わり」、または入口なしで 1 回表示）。ユーザーの別案は数字で比べて評価し、よければ採る。「まとめて」と頼まれたら、その画面でやることを 1 ページにまとめる |
| 4. カーソルで説明文を読む | 今の内容 |
| 5. 知見（notes） | 最初に `notes/README.md`（索引）を開き、該当するアプリのフォルダの README を読む。なければ `references/notes-format.md` の型でフォルダを作り、索引に足す。カーソルで読んだ説明文はその場で書く。分からないことはウェブで調べ、出典の URL を添える。教わったことと結果はセッションの終わりに書く |
| 6. 場面別の手引き | ゲームの相談・プレイの案内は `references/playbook-game.md`、アプリの操作・設定の案内は `references/playbook-app.md` を読む |

`description`（スキルを使う場面）は、ゲームとアプリ操作の両方を挙げ、`docs/games/` の記述を `notes/` に替える。

### 6.2 `references/playbook-game.md`（ゲームの案内）

STS2 の 3 回のセッションの教訓から、どのゲームにも通じるものをまとめる。

- 1 ページに、その手番（ターン）でやること一式を ①②③ の順で書く。ボタンは「ターン終了した」など、済ませた操作の名前にする。入力欄も出す
- 勧める前に、状態をひととおり読む: 自分の体力・資源、相手の予告（意図）、状態異常、持ち物・消耗品。分からない表示はカーソルで読む
- 数を数えてから勧める: 受けるダメージと守り、与えるダメージと相手の体力。計算を説明文に書く
- 選択肢には、手札や主な操作だけでなく、消耗品や持ち物（ポーション、レリックなど）も入れる
- 長期の損得（デッキや持ち物を増やす、スキップする、休む・強化する）は、数字で比べる。取らない選択も勧めてよい
- 「ターン終了した」が押されたら、撮り直し画像で手番が進んだか（ターン数、資源）を確かめる。演出中なら数秒おいて撮り直す
- 仕組みを思い込まない。説明文を読むか調べてから勧める
- ユーザーの指摘や別案は、正しいことが多い。採ったら、教訓として notes に残す
- 1 回のプレイ（ラン）の結果と敗因は、`sessions/` に残す

### 6.3 `references/playbook-app.md`（アプリ操作の案内）

- 最初に、ユーザーが最終的にしたいことを確かめる
- 撮影は基本 `capture_monitor`（ダイアログ・メニュー・ツールチップが別ウィンドウで出るため）
- 1 ページに 1 手順。押す場所を枠と番号で示し、説明文には画面に見えているとおりの表記でメニューの道筋を書く。「まとめて」と頼まれたらまとめる
- 「できた」のあと、撮り直し画像で結果（ダイアログが開いた、設定が変わった）を確かめる。違っていれば、同じ手順を詳しく出し直す
- 取り消せない操作（削除、送信、購入、上書き、インストール、セキュリティに関わる設定）の前は、何が起きるかを説明文に書き、ページのボタンで確認をとってから案内する
- 画面が想定と違う（バージョンや言語の違い）ときは、そう伝えてウェブで調べる
- メニューや設定の場所、バージョンの違い、つまずいた点を notes に残す

### 6.4 `references/notes-format.md`（知見の書き方）

- フォルダの型

  ```text
  notes/
    README.md                索引（アプリ名・フォルダ・見分け方）
    <アプリ>/
      README.md              アプリ全体: 概要、画面の見方（領域と座標の目安）、ルールと注意、用語、未確認
      <区分>/ や <区分>.md   キャラ、敵、イベント、持ち物、作業の流れ、設定 など
      sessions/<日付>-<内容>.md  その回の記録: 結果、判断、失敗の原因
  ```

- フォルダ名は英小文字とハイフン（例: `slay-the-spire-2`、`excel`）
- 置き分け: アプリ共通の事実は README か区分ファイル。区分に固有のことは区分ファイル。その回の出来事は `sessions/`。アプリを問わない使い方のコツは notes に書かず、スキルの手引きの改善として提案する
- 確かさの印: 確実（画面の説明文）、観察（数字で確かめた）、ユーザーの教え、推測。調べたことには出典の URL
- 書く時: カーソルで読んだ説明文はその場で。ユーザーの指摘はその場で。結果と教訓はセッションの終わりに
- アプリの README のひな形を載せる

### 6.5 `references/annotation-html.md`

変えない（すでに汎用）。

## 8. テストと確認

自動テスト（`uv run --no-sync pytest -q`、今の 151 件を含めて全件 PASS）:

- `tests/test_viewer.py`: 待ち受け中に `refresh()` すると `{"message": "", "via": "refresh"}` が返る。待ち受けていないとエラー。HTTP の `/refresh` が動き、トークン・`Origin` のない要求は拒否される
- `tests/test_annotate.py`: ページに「更新」ボタンがあり、待ち受け中だけ押せ、`/refresh` に送る
- `tests/test_server.py`: `html` が空や空白でも表示できる。`buttons` に「更新」があればエラー。`wait_for_message` が `via: "refresh"` を撮り直し画像と一緒に返す。`INSTRUCTIONS` に更新ボタンの説明がある
- `tests/test_captures.py`: 既定の保持数が 20
